# TASK-2026-016 handoff

## Purpose

Make a fresh install ship with a blank AI-provider configuration — no
providers, no default provider, nothing enabled, and no boot-time LLM gate —
so a new clone starts cleanly and the operator configures a provider
explicitly through the Settings UI. Previously the schema seeded 4 providers
(2 enabled → localhost:8000/8001) and gated startup on LLM reachability,
which paused a fresh install against services that never existed.

## Changes made

- `aletheia/config/schema.py`:
  - `ModelsConfig.providers` → `Field(default_factory=dict)` (was 4 seeded stubs).
  - `ModelsConfig.default_provider` → `""` (was `"openai_compatible"`).
  - `ProviderConfig.enabled` → `False` (was `True`; opt-in).
  - `HealthConfig.require_llm_at_startup` → `False` (was `True`).
- `aletheia/model_provider/router.py`: `get_provider` / `get_provider_async`
  now raise a human-actionable "No LLM provider configured. Add and enable one
  under Settings → AI Model Providers" when the resolved name is empty, instead
  of a confusing `Unknown provider: ` (empty name).
- Test fixtures reseeded to the blank-default world (they previously relied on
  the auto-seeded providers): `test_doctor.py` (3 creds tests),
  `test_model_provider.py` (router default/anthropic/codex + secret_ref),
  `test_model_fallback.py::_setup_config`, `test_codex_provider.py`,
  `test_config_routes.py` (get-model + 2 test-candidate), `test_acceptance.py`
  (ac06). `test_startup_gate.py::_cfg_with` now persists to disk and enables the
  gate, so the lifespan reload sees `require_llm_at_startup=True` (mirrors
  production, where config.yaml always exists on disk).
- New tests: `test_config.py` — fresh-blank assertions (empty providers/default,
  `ProviderConfig` opt-in, gate off, bootstrap stays blank) and
  existing-config-not-overwritten; `test_model_provider.py` — clear error when
  no provider configured.

## Risks

- Behavioral change for a hand-trimmed config.yaml that has a `models:` block
  but OMITS the `providers:` key: it now yields `{}` instead of the old
  localhost stubs. The real committed config.yaml has an explicit `providers:`
  key, so this does not affect live installs — flagged for completeness only.
- A fresh install cannot run any LLM-driven agent until the operator configures
  a provider. This is intended (and now fails loud with a clear message rather
  than silently pausing), but it means first-run agent jobs return
  `llm_unavailable` until setup — surfaced honestly in /api/health and the UI.
