## 一、最完整的系统架构：s1-s7 模块化（photo_138，含金量第一）

一位群友的 VSCode 工程目录 `AI_TRADE/`，揭示了一套**模块化七件套**架构（文件名直接说明各模块职责）：

```
AI_TRADE/
├── s1_binance_alpha_monitor.py        # 币安 Alpha 新币监控
├── s2_oi_funding_rate_scanner.py      # OI + 资金费率 扫描器
├── s3_accumulation_radar.py           # 庄家收筹/热度做多雷达
├── s4_voicekey_speaker_verification.py # 声纹/身份验证（语音口令？）
├── s5_on_chain_narrative_radar.py     # 链上叙事雷达
├── s6_futures_alpha_autonomous_trading.py # 合约 Alpha 自主交易
└── s7_vitalik_sell_radar.py           # Vitalik 抛售雷达（巨鲸/特定地址监控）
```

### s3 模块头部注释（完整逻辑，可直接复用）
```python
#!/usr/bin/env python3
"""
热度做多雷达 v2 — 热度 + 费率 + OI 三维扫描

核心逻辑（拉哪模式）：
1. 热度先行 → CG热搜 + 放量 = 资金涌入信号
2. 负费率 = 空头燃料，庄家拉盘爆空单
3. OI暴涨 = 大资金建仓 = 即将拉盘

单策略：发现热度 → 小仓做多 → 严格止损 → 拿住赢家

数据源：币安合约API + CoinGecko Trending（零成本）
"""

import json, os, sys, time, requests
from datetime import datetime, timezone, timedelta
from pathlib import Path
from square_heat import get_square_heat   # 自定义模块：广场热度

# === 加载 .env ===
env_file = Path(__file__).parent / ".env.oi"   # 注意：用 .env.oi 分离不同采集器的配置
```

> **架构精髓**：
> - **职责单一**：每个 `sN_*.py` 只干一件事（监控/扫描/雷达/交易），互不耦合。
> - **零成本数据源**：币安合约 API（免费）+ CoinGecko Trending（免费热搜）。
> - **`.env.oi` 分文件管理密钥**：不同采集器用不同 env 文件，降低耦合。
> - `square_heat.get_square_heat`：自建的「广场热度」模块（爬币安广场/X 提及次数）。注意：这个模块是自己写的，群里很多人问「square_heat 在哪下载」→ **答案：是作者自定义的，不是公开包**。

## 四、影子开仓 / 纸面回测面板（photo_185，「pump_short 专区」）

一种叫 **「影子开仓（shadow trading）」** 的纸面验证机制——不真开单，但用实时价模拟跟踪：

### 顶部汇总条
```
pump_short 专区 | 总数 17 | 观察中 0 | 已平仓 17 | 胜率 64.71% | 盈亏 +41.4226 U
```

### 表格列
| ID | 币种 | 信号 | 方向 | 级别 | 入场 | 止损 | 止盈 | 来源 | 状态 | 盈亏 | 时间 |
|----|------|------|------|------|------|------|------|------|------|------|------|
| #S098 | EDENUSDT | pump_short | 做空 | B | 0.06264 | 0.072036 | 0.050112 | 影子开仓 | 已结束 | +6.0057U | ... |

> **「影子开仓」的价值**：浪里个浪原话——「开仓没做限制，就是为了多些开单数据，现在这点数据连自训练都不行。」即**用影子单大量积累样本喂给 ML 模型/复盘**，而不冒实盘风险。这是模拟盘的进阶替代（自建、按实时数据平仓，比交易所模拟盘更可控）。
> - 人世间同理：「我都是让 AI 自己弄个模拟盘脚本，只看 AI 推的信号出来的市价，买入后计算止盈止损浮盈浮亏」「跑数据喂 hermes」。

## 五、做空系统状态查询（photo_205/206，Telegram 交互式查询）

通过给 bot 发「盈亏」「盈亏比胜率都统计一下」等指令，返回系统状态。两种口径设计很专业：

### 「做空系统 V1 状态」（photo_206）
```
观察池: 5
当前持仓: 27笔 | 名义 10452.34U | 对冲 0笔
当前持仓净浮盈: +70.18U (+0.67%)
已平仓盈亏: +362.63U | 今日 +89.89U | 已平仓 4笔
合计估算盈亏: +432.81U
分类浮盈: A:2笔 +202.07U | B:3笔 +47.22U | C:22笔 -179.11U
当前最好: #BILLUSDT +101.08U
当前最差: #PHAUSDT -53.94U
```

### 双口径盈亏统计（photo_118，最值得抄的统计逻辑）
```
【当前持仓口径】
胜率: 17赢 / 34持仓 = 50.0%
盈亏比: 1.95
总浮盈: +843.27U  总浮亏: -431.61U  净浮盈: +411.66U
平均盈利单: +49.60U  平均亏损单: -25.39U

【含已实现盈亏口径（5/10至今，按币种合并）】
胜率: 16赢 / 35个币 = 45.7%
盈亏比: 1.91
总盈利: +1267.71U  总亏损: -664.86U  净收益: +602.85U

简单说：胜率一般，但盈亏比接近2，靠大盈利单把整体拉起来了。
```

> **统计面板设计精髓**：
> 1. **双口径**：持仓口径（含浮盈）+ 已实现口径（按币种合并），避免单一口径骗自己。
> 2. **信号分级浮盈（A/B/C）**：按信号等级统计，能看出哪个等级真有 edge（如上面 A、B 级浮盈为正，C 级 -179U → C 级信号该砍）。
> 3. **平均盈利单 / 平均亏损单**：直接体现盈亏比的来源。
> 4. **最好/最差持仓**：一眼定位拖后腿的标的。

## 七、技术栈与工程要点（群内共识）

| 环节 | 群内主流选择 | 备注 |
|------|------------|------|
| 语言 | **Python**（AI vibe coding 生成） | 张德楷：「推荐 python，AI 太笨了」指别让 AI 实时决策，而是写 py |
| 行情数据 | 币安合约 API（免费）/ WebSocket 推送 | zh1p4ng：「多用 ws 的数据，API 降低频率，不同类型采集要区分」 |
| 市值数据 | **CoinGecko 接口**（不要用币安 web3 api） | Wiggins 踩坑：币安 web3 api 取的是链上总市值，含同名代币，错乱 → 改 CoinGecko |
| 高级数据 | **Coinglass API**（公认最全） | 张德楷：「最简单的办法，Coinglass 的 api 什么都有了」；Wiggins 准备去闲鱼搞专业版 |
| 数据库 | SQLite（让 AI 建表填数据） | zh1p4ng：「描述需求让 AI 先建表，让 AI 扫一遍往 DB 填数据，找不到的你补充」 |
| 币种映射 | 维护一张「链上名 ↔ 合约名」映射表 | zh1p4ng：「做个映射表，过几天维护一次就可以」（合约名和链上名常不一致） |
| 部署 | VPS（详见 [08](08_工具数据源与避坑清单.md)） | 本地打磨 → 迁移到云端跑（YM：「本地优化，云端跑」） |
| 大模型 | DeepSeek（跑信号）+ Claude/Codex（写代码/复盘） | **分层架构**，省 token |

### 分层架构思想（核心省钱 + 稳定原则）
张德楷：「**分层架构**就行了」；PIZZA：「官方跑交易肯定烧不起」。

> **黄金分层模式（人世间、热宝反复强调）**：
> 1. **策略脚本本地/云端定时跑，不消耗 token**（参数定好后纯 Python 计算）。
> 2. **行情监控用便宜模型（DeepSeek）**——「监控这种不怎么用技术的交给 ds」。
> 3. **复盘、改代码才用贵模型（Claude/Codex）**。
> 人世间实测：这样跑 10 天、烧了 15 亿 token，DeepSeek 只花了 ~100 块；如果全用 Claude 「token 费不得上天」。

## 八、PIZZA 的系统（最清晰的一句架构总结）

群里被反复请教的 PIZZA（女菩萨），5/28 亲口说明她的系统：
> 「我是自己做了一个 **Python 系统在服务器上跑**，然后系统里面接了 **Claude 的大模型**。」
> 「自己设计的。」
> 多周期判断：「**15m 看入场、1h 看主结构、4h 看 30 天大区间、日线看 90 天大级别位置。AI 看到的是压缩后的关键摘要，不是把所有 K 线原样塞进去。**」
> 跑了快一个月实盘，多空都做，平均一天约 10 单（开+关算 2 单 → 实际约 5 个来回）。

> **关键工程点**：「AI 看到的是**压缩后的关键摘要**，不是原始 K 线」——这是控制 token + 提升信号质量的核心技巧。不要把几百根 K 线塞给模型，而是先用代码算出结构摘要（BOS/OB/FVG/关键位）再喂。
