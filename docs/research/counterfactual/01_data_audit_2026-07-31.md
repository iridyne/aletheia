## 2. L0 完整性缺口

### 2.1 `policy_epoch_id` 列缺失（P1）

```sql
PRAGMA table_info(shadow_trades);
-- policy_epoch_id 列不存在
```

**根因**：`aletheia/storage/migrations.py` 中 `_ADDITIVE_COLUMNS` 列表包含 `("policy_epoch_id", "shadow_trades", "TEXT")`（PR #503 引入），但此 dev DB 的迁移未执行。

**影响**：
- CF-I04（Epoch 分层不变量）无法验证
- `calibration.build_calibration(policy_epoch_id=...)` 查询会抛 `sqlite3.OperationalError`
- 跨 epoch 分析当前没有数据基础

**修复路径**：执行 `aletheia.storage.migrations.run_additive_migrations()` 即可；无数据丢失风险（仅 ADD COLUMN）。

### 2.2 `scanner_family` 列存在但分布完整

所有 35,726 行均有 scanner_family 值，六个 family 覆盖率 100%。

## 3. L1 结算质量

### 3.1 现代 shadow 行的结算路径（重要）

与老版本（pre-b9ad957）不同，当前所有 shadow_trades 行都有 `outcome_candidate_key`，其主结算路径是：

```
filter_outcome_recorder.settle_due()
    → settle_filter_candidate_outcome(fco_id, horizon="24h", ...)
    → settle_linked_shadow_outcomes(outcome_candidate_key)  ← 批量更新所有同 key 的 shadow 行
```

`resolve_stale_shadows`（scheduler `shadow_resolver` 6h job）只处理 `outcome_candidate_key IS NULL` 的历史孤儿行，在本 DB 中**没有任何孤儿行**，所以跑它结果是 0——这是正确行为，不是 bug。

### 3.2 待结算行的根因分类（5,474 distinct keys，25,032 raw 行）

| 24h FCO 状态 | distinct keys | % | 说明 |
|---|---|---|---|
| `pending` | 5,002 | 91.5% | filter_outcome_recorder 尚未完成 OHLCV 抓取 |
| `failed` | 441 | 8.1% | 24h OHLCV 不可得 → **永久无法结算**（设计上可接受） |
| `settled` 但 shadow 未更新 | 31 | 0.6% | 潜在 race condition 或一次性延迟 |

**结论**：91.5% 的 pending 行等待 `filter_outcome_recorder.settle_due()` 运行；这是运营可达状态，不是积压问题。441 行因 24h FCO failed 而永久 pending（价格不可得 = 证据缺失），是设计上明确的 failure semantics。

**P1 修正**：原始诊断"shadow_resolver 停止"是误判。正确的 P1 是：**验证 `filter_outcome_recorder.settle_due()` 在目标环境（CASI/主实例）是否定期运行**。

### 3.3 结算来源

| settlement_price_source | 行数 | 说明 |
|---|---|---|
| NULL | 25,032 | 待结算（24h FCO 尚 pending 或 failed） |
| `horizon_ohlcv` | 10,694 | filter_outcome_recorder 通过 OHLCV 结算后联动更新（**主路径**） |
| `late_ticker` | 77 | 推测为 position_close 路径的变体（dev 环境极少发生） |

注：`position_close` 来源未出现，说明 dev 环境没有实盘 Position 正常关闭触发 `resolve_shadow_trades_for_position`。

### 3.4 结算延迟分布（已结算行）

| 指标 | 值 |
|---|---|
| 平均结算延迟 | 29.1 小时 |
| 最短延迟 | 0.0 小时（immediate） |
| 最长延迟 | 115.9 小时（~5 天） |

29h 平均延迟高于 24h horizon，符合预期：backfill job 以 6h 为周期，最坏情况是 horizon 到期后还要等 6h + OHLCV 数据可用延迟。

### 3.5 整体结算率

10,694 / 35,726 = **29.9%**。看似低，但逻辑正确：settled 行来自 2026-07-15 的早期 candidates（24h horizon 在记录后 1 天内到期，filter_outcome_recorder 当时在运行）；2026-07-22 之后创建的 candidates 对应 FCO 多为 pending，等待 OHLCV 数据（dev 环境 filter_outcome_recorder 已停止）。若 filter_outcome_recorder 常驻，预期最终结算率 > 90%（441 failed FCO 是永久损失的 8%）。

## 4. trade_score 分布（已结算行）

| 指标 | 值 |
|---|---|
| 最小值 | -20.4 |
| 最大值 | **69.4**（从未触及 70） |
| 均值 | 51.3 |

**观察**：`trade_score` 的现实上界约为 69。`calibration.py` 定义的 70+ 频段（`_BAND_EDGES[-1] = 70.0`）在当前数据中没有样本。

这可能意味着：
1. ranker 的原始 score 经 `min(..., 95)` 裁剪后，在当前市场环境/候选池中自然落在 [20, 70] 区间；
2. 70+ 频段分析需要更长时间（更多市场环境）或 ranker 行为变化。

## 附录：复现查询

```python
# L0 migration check
import aletheia.storage.sqlite as db
conn = db.get_db()
cols = [c[1] for c in conn.execute("PRAGMA table_info(shadow_trades)").fetchall()]
assert "policy_epoch_id" in cols, "migration not applied"

# L1 settlement rate
total = conn.execute("SELECT count(*) FROM shadow_trades").fetchone()[0]
settled = conn.execute("SELECT count(*) FROM shadow_trades WHERE net_pnl_pct IS NOT NULL").fetchone()[0]
print(f"{settled}/{total} = {100*settled//total}%")

# Overdue pending
from datetime import datetime, timezone, timedelta
cutoff = (datetime.now(timezone.utc) - timedelta(hours=25)).isoformat()
overdue = conn.execute(
    "SELECT count(*) FROM shadow_trades WHERE net_pnl_pct IS NULL AND created_at < ?",
    (cutoff,)
).fetchone()[0]
print(f"overdue: {overdue}")
```
