# 生命周期能力地图：长期维护的开发指引（提案）

> 提案状态：**accepted**（owner 2026-10-09 批准，采用 AI 盘点、不写脚本的版本）。本文是设计，不代表已经实现。

## 摘要

Owner（2026-10-09）提出了以下要求：
- 以"一次交易机会 / 一个持仓的完整生命周期"为主线，做一份能力地图；
- 地图要回答三个问题：框架现在能做什么、应该能做什么、还缺什么；
- 地图要**长期更新**，持续为开发方向提供指引；
- 地图要和 open issues 结合；
- 做法要参考大型工程项目的最佳实践。

本提案给出满足上述要求、同时遵守仓库文档治理规则的做法：**稳定的定义写进文档，进度和优先级放在 GitHub，"当前做到哪一级"由 AI 按固定流程定期盘点并给出证据，结果贴到 issue 上，不提交进仓库。**

## 当前事实

- **治理约束**：`documentation_governance.md` 规定文档里不得出现实时状态、进度或优先级。新增登记表需要有"具体失败"作为证据，并由 owner 写入决策记录。
- **可复用部件**：
  - `ACTIVE_RUNTIME_SCOPE.md` 的 YAML 头部已经是机器可读的因果链；
  - `check_docs.py` 已经能校验文档里提到的符号和路径是否真实存在；
  - `capability-integrity/AUDIT_METHOD.md` 已经定义了 E1/E2/E3 三级证据。
- **GitHub 的具体失败**（2026-10-09 实测）：
  - open issue 共 615 个，其中 `priority/now` 52 个、`priority/soon` 242 个，owner 的优先级信号被冲淡了；
  - 没有任何"生命周期阶段"或"能力"维度的标签，`area/runtime` 一个标签就覆盖了 299 个 issue；
  - 标签重复（例如 `admission` 和 `area/admission`），有的标签描述已经过时；
  - 原生的父子 issue 功能使用量为 0。

## 设计

### 1. 文档里放什么（稳定内容）：`docs/product/CAPABILITY_MAP.md`

- **11 个生命周期阶段**：候选、规划、入场计划、触发、提案、风控、执行、持仓管理、平仓结算、结果度量、复盘学习。每个阶段都对应到 `ACTIVE_RUNTIME_SCOPE` 因果链上的一环。
- **能力编号**：格式为 `CAP-<阶段>-<序号>`，例如 `CAP-RISK-01`。编号一旦分配就永不复用，退役的编号单独列出。
- **每项能力写明**：
  - 要达成的结果；
  - 对应的契约；
  - owner 设定的目标级别；
  - 探针，包括代码符号、生产调用方、测试；
  - 达到最高级别的资格标准。
- **成熟度阶梯**：文档里只定义每一级的判据，**不写当前处于哪一级**。

  | 级别 | 判据 |
  |---|---|
  | L0 缺失 | 没有生产代码 |
  | L1 休眠 | 代码存在，但没有生产调用方，或默认关闭 |
  | L2 接通 | 入口、持久化、下游消费方都接通，并有跨接缝的测试（E1 + E2） |
  | L3 观察到 | 在已部署的具体版本上自然发生过（E3） |
  | L4 合格 | 满足资格标准，并由 owner 接受。脚本永远不会自动判为这一级 |

- 首版只登记主线上的能力，每段 2～3 项，共约 25～30 项。

### 2. GitHub 上放什么（会变化的内容）

- **一个缺口对应一个 issue**，正文开头写一行 `Capability: CAP-XXX-nn · Target: L2`，并打上 `cap/CAP-XXX-nn` 标签。
- **优先级**沿用 `priority/now`、`priority/soon`、`priority/later` 和 `wip/delivery`。**只有 owner 能设置或移除 `priority/now`**；AI 新建的 issue 不带优先级。
- **一个路线图总 issue**，专门承载每周的评审纪要。
- GitHub Project 看板和各阶段的父子 issue 留到第二版再做。

### 3. 当前状态由 AI 定期盘点得出（owner 2026-10-09 决定：不写生成脚本）

- **为什么不写脚本**：Owner 认为，判断"一项能力有没有真正接通、Fedora 上的证据算不算数"需要读懂代码、结合契约和运行数据，脚本做不到；而且脚本里的探针会随代码改动失效，最后变成过度工程、没人维护的负担。
- **做法**：把盘点流程固定为一条可复用的斜杠命令 `.claude/commands/capability-review.md`，和现有的 `start-session`、`project-audit` 并列。每次运行，AI 都按同样的步骤：
  1. 读登记表；
  2. 查代码和测试；
  3. 查 Fedora 上的只读证据；
  4. 查相关 issue；
  5. 输出每项能力的级别、证据和对应 issue，以及"给 owner 的建议候选"。
- **盘点结果**：作为评论贴到固定的路线图 issue 下，不提交进仓库。
- **唯一的自动检查（可选）**：只在 `check_docs` 里校验登记表格式和编号是否唯一，不检查任何状态。

### 4. 节奏与分工

| 角色 | 职责 |
|---|---|
| Owner | 增删能力、调整目标级别（D1）；设置 `priority/now`；接受 L4 级别；每周评审一次 |
| AI | 每次会话开始时跑一次地图，确认当前任务属于哪项能力；PR 里写明对应的 Capability；发现没人认领的缺口时可以新建 issue，但不自行开工 |
| 盘点 AI | 按 `/capability-review` 流程给出级别和证据，报告漂移；只在路线图 issue 上发评论，不改文档 |

地图里会有一节"给 owner 的建议候选"，排序规则是**越靠因果链上游、越低于目标级别的越优先**。这一节只是给 owner 的参考证据，不是工作队列，AGENTS.md 中"AI 不得自选无关积压工作"的规则保持不变。
