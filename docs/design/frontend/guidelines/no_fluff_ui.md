# No Fluff UI Guidance

本文件是 Aletheia 前端的长期设计准则。它把 [No Fluff 写作指令](https://nofluff.0x01.me/)
转成可检查的界面规则，适用于页面结构、标签、空状态、告警和详情层级。视觉 token、布局和组件
规范仍以 [UI Design System](ui_design_system.md) 为准。

## 两个检查

每个界面元素都必须通过两个检查：

1. 删除它以后，用户是否会失去判断或完成任务所需的信息？没有损失就删除。
2. 用户追问“这具体是什么意思”时，界面能否给出事实、口径或下一步？不能就改成具体事实。

这两个检查适用于标题、卡片、指标、按钮、说明文字、颜色和图表，不只适用于正文。

## 先回答用户问题

页面按用户要完成的判断组织，不按数据库表、API 或内部模块组织。首屏优先回答：

- 当前状态是什么；
- 最近发生了什么变化；
- 变化是否产生可测结果；
- 现在需要用户处理什么。

内部 ID、版本、哈希、查询窗口和完整证据放进详情。只有它们直接改变当前判断时才进入首屏。

## 用事实代替保证

不要写没有当前误解需要纠正的保证，例如“No silent zero”“not effectiveness”或“This page does
not mutate state”。直接显示可验证事实，例如数据更新时间、样本数、权限状态和可用动作。安全边界
只有在用户将要执行相关动作或一个指标容易造成具体误判时才显示。

不要用颜色代替文字。`0`、`Unavailable`、`Disabled`、`Never run` 和筛选后无结果必须是不同状态。
失败的读取不能显示成 0 或正常空态。

## 指标必须支持判断

单独的数量通常只是库存，不是结论。指标至少要提供下面一项上下文：

- 比较对象；
- 时间窗口；
- 目标或阈值；
- 相比上一次的变化；
- 需要采取的动作。

例如“Guard candidates 430”需要说明这是待审核积压；实验样本需要同时显示门槛和剩余数量。
无法支持判断的统计放进详情或删除。

## 删除重复和无归属内容

同一数据不要因为不同模块都能读取就在多个页面重复出现。每种信息应有一个主要归属：

| 信息 | 主要归属 |
|---|---|
| 最近学习产物 | Learning Overview |
| 实验效果和证据 | Learning Impact |
| 历史知识检索 | Learning Library |
| 运行、失败和数据管道 | Learning Operations |
| 普通账户盈亏 | Cockpit 或 Trades，不属于 Learning 贡献 |

当一段说明需要不断增加限定语才能合理存在时，先检查对应卡片是否应该删除或移入详情。

## 空状态必须说明原因

空状态至少区分：功能禁用、从未运行、已运行但没有输入、已运行但没有产出、读取失败、筛选无匹配。
有事实支持时，同时显示最后成功时间、下一次运行时间和恢复条件。没有持久化事实时写“Not recorded”或
“Not available”，不要根据时间接近、标题相似或总数推断因果关系。

## 渐进披露

首屏显示结论、原因、证据缺口和下一步。详情显示身份、来源、原始记录和诊断字段。一个成熟的首屏
不要求用户理解内部 schema 才能知道系统是否正常、是否有效、是否需要操作。

## Review Checklist

- 页面标题能否说明用户来这里做什么？
- 首屏是否在 30 秒内回答状态、变化、效果和待办？
- 每个指标是否有窗口、比较、目标或动作？
- 是否把活动量误写成效果或贡献？
- 是否存在重复卡片、重复说明或无动作价值的字段？
- 空状态是否区分禁用、未运行、无产出、失败和无匹配？
- 来源和因果关系是否来自持久化关联，而不是界面推断？
- 重要动作是否可用键盘完成，状态是否不依赖颜色表达？
- 窄屏是否保持与桌面相同的阅读顺序和信息优先级？
