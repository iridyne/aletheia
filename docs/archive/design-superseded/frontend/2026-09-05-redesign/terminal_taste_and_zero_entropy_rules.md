## 一、 核心认知纠偏：什么是“品味（Taste）”？

在专业金融终端（Bloomberg、TradingView、CME、ICE、TT）的设计哲学中：

```
┌────────────────────────────────────────────────────────────────────────┐
│ ❌ 低品味 / 消费级 SaaS 杂音 (信息熵 ≈ 0)                             │
│    • "• 衍生品体征 (物理落库): 资金费率: +0.01% (年化10.9%)"          │
│    • "• 订单簿抽样 (20档汇总): 10bps深度: $118k"                       │
│    • "提示：该指标由后台 OHLCV 实时自研算法生成"                      │
├────────────────────────────────────────────────────────────────────────┤
│ ✅ 顶级金融终端硬核美学 (高信息密度，纯粹事实)                       │
│    FR 0.0100% (10.9% ANN)   OI 1H +1.8%   SPREAD 2.2 bp   D10 $118k   │
└────────────────────────────────────────────────────────────────────────┘
```

* **专业假定（Professional Assumption）**：
  用户清楚地知道什么是 Funding Rate，什么是 Volume Profile，什么是 10bps 深度。不需要你假惺惺地在括号里加上“（物理落库）”去证明你的技术实现，更不需要加“（20档汇总）”去展示数据口径。
* **数据墨水比（Data-to-Ink Ratio）**：
  屏幕上墨水消耗在“解释这个数据是什么”的字符越多，真正有价值的“数值本身”就被稀释得越严重。每一个像素都必须用来呈现市场本身。

## 二、 必须彻底消灭的四大“低品味”设计顽疾

### 1. 顽疾一：生造汉语杂糅定语（如“衍生品体征”、“微观体征”）
* **反面**：`衍生品体征: 资金费率: +0.01%`
* **病根**：用空洞、抽象的生造词充当分类标题。
* **正解**：直接拿掉大分类，直出标准金融缩写：`FR +0.0100%`。

### 2. 顽疾二：技术实现向外暴露（如“（物理落库）”、“（OHLCV计算）”）
* **反面**：`筹码结构 (OHLCV计算): POC $4.52`
* **病根**：把开发者的内部实现细节、数据库落库动作，当成宝贵信息塞给操作员。这是典型的“以自我为中心”的技术自嗨。
* **正解**：直接呈现：`POC 4.5200`。交易员只关心控制线在哪，不关心你是用什么算的。

### 3. 顽疾三：自相矛盾的自我声明（如“No silent zero”、“安全运行中”）
* **反面**：在卡片底部写一段小字：“本页面绝不篡改底层数据，严格保持只读”。
* **病根**：没有误解却强加解释，属于典型的废话（Fluff）。
* **正解**：彻底删除该类说明文字。系统本来就该只读，无需写标语自证清白。

### 4. 顽疾四：列表与表格中的冗余括号与项目符号
* **反面**：使用带有装饰性的圆点符号（`•`）去罗列本该横向对齐的金融数据。
* **正解**：使用标准等宽网格（Grid）横向排开，用微弱的冷灰中点（`·`）或竖线（`|`）做视觉对齐。

## 三、 标准金融代号与命名矩阵（Financial Notation Matrix）

全站必须严格遵循国际金融与加密市场的公认标准代号，严禁自创冗长名词：

| 指标全称 | ❌ 严禁使用的低品味文案 | ✅ 唯一允许的标准金融展示形式 |
|---|---|---|
| **资金费率 (Funding Rate)** | 衍生品体征(物理落库): 资金费率 | `FR: 0.0100%` 或 `FUNDING: +0.0100%` |
| **持仓量 (Open Interest)** | 合约持仓变化量 | `OI: $83.6M` / `OI 1H: +1.8%` |
| **盘口点差 (Bid-Ask Spread)** | 订单簿抽样: 点差 | `SPREAD: 2.2 bp` |
| **紧密深度 (10bps Depth)** | 20档汇总深度金额 | `D10: $118k` 或 `DEPTH 10BP: $118k` |
| **盘口倾斜度 (Imbalance)** | 订单簿买卖倾斜比 | `IMB: +0.14` |
| **成交量最大分布价 (POC)** | 筹码结构(OHLCV计算): POC | `POC: 4.5240` |
| **价值区下轨 (Value Area Low)** | 筹码价值区低位 | `VAL: 4.4100` |
| **价值区上轨 (Value Area High)**| 筹码价值区高位 | `VAH: 4.7500` |
| **已实现盈亏 (Realized PnL)** | 实际结算盈亏金额 (USDT) | `REALIZED: +$10.17` |
| **未实现盈亏 (Unrealized PnL)**| 实时浮动未结算盈亏 | `uPnL: +$120.40` |


## 五、 前端开发 Review 铁律清单（Checklist）

所有新提 PR 或代码重构必须通过以下审查，凡命中任何一项立即驳回：

- [ ] **严禁元说明**：界面文字中是否出现了“（计算）”、“（抽样）”、“（物理落库）”、“（自研）”？
- [ ] **严禁空泛修饰词**：是否使用了“体征”、“画像”、“概貌”等模糊文学化词汇？
- [ ] **代号规范化**：是否使用了标准的 `FR`、`OI`、`POC`、`VAL`、`VAH`、`SPREAD`？
- [ ] **信息熵审查**：删除这段文字后，操作员是否会做出错误的交易决策？如果不会，**立即删除**。
- [ ] **严禁假定用户是新手**：文字是否在像说明书一样教用户怎么读指标？专业终端只出事实。
