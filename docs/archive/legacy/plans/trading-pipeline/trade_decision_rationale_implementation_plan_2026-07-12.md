# 交易开平仓理由链实施计划

> 目标：把现有“机会为什么被选中”的追溯能力，延伸到每笔交易的开仓与平仓；让操作者能在同一条因果链里看清每个关键数值是谁给出的、为什么这样取值、最终实际执行了什么。

## 1. 本次要解决的问题

当前系统已经保存机会、交易提案、风控决定、订单、成交和仓位的关联 ID，也会保存一段总的交易判断。但是下列信息没有形成逐项、可核验的记录：

- 入场价为什么合适；
- 止损和止盈为什么放在该位置；
- 名义价值为何是该金额，以及按止损估算最多亏多少；
- 杠杆为何请求该倍数、最后是否被系统上限收紧；
- 平仓究竟来自 AI 的新判断、预先设定的保护规则、人工操作，还是对账收敛。

因此，页面虽然能看到参数和笼统判断，却不能诚实回答“这个数值是谁决定的、依据是什么、平仓时是否真的有新的 AI 判断”。

## 2. 设计原则与边界

### 要保护的边界

- 只增强决策记录和只读展示；订单仍只经过 Execution Gateway，风险引擎的限额、审批和执行模式不变。
- 不增加交易所、配置项、风险限额、凭证访问、实盘开关或任何直达下单路径。
- 保留已有提案哈希保护：开仓参数说明放进提案的不可变理由内容，成为被保护内容的一部分。
- 不把系统计算、默认值、上限收紧或对账事实伪装成 AI 的主观理由。
- 旧记录不回写补故事；侧栏明确显示“未记录”。

### 触及的模块

- 高敏感决策链：`agent_shell/trading_decision.py`（AI 输出、最终参数和理由快照）。
- 状态记录：`storage/models.py`、`storage/migrations.py`（新增仓位平仓说明字段）。
- 仓位生命周期：`portfolio/pnl.py`、`portfolio/position_manager.py`、`portfolio/outcome_closure.py`（只记录平仓说明，不改变何时或如何平仓）。
- Dashboard：`frontend/src/components/CausalChain.tsx`、类型与样式（只读展示）。

不触及 `risk/`、交易所客户端、凭证、权限、实盘解锁或订单路由语义。

## 3. 记录格式

### 3.1 开仓：提案理由中的 `entry_parameters`

System Operator 的结构化输出新增五条简短理由。创建提案时，后端将其与已解析的最终数字组合为一个 JSON 快照，存入现有 `agent_rationale` 的元数据部分：

| 要素 | 保存的事实 | 说明来源 |
|---|---|---|
| `entry_price` | 请求/实际入场价、目标市场 | 最新市场快照；AI 解释为什么现在入场 |
| `stop_loss` | 最终止损价、距离和止损金额估算 | AI 的失效条件；标明是 AI 给值还是默认比例 |
| `take_profit` | 最终止盈价、目标距离 | AI 的兑现目标；标明是 AI 给值还是默认比例 |
| `notional_usdt` | 请求名义价值、按数量和价格算出的实际名义价值、止损预计亏损 | AI 的仓位理由；系统的算术结果独立标记 |
| `leverage` | 请求倍数、最终倍数、适用上限及是否被收紧 | AI 的理由；现货固定为 1x，永远不假称 AI 选择了杠杆 |

字段中同时有 `value_source`（AI 输入、市场快照、默认值、上限收紧或不适用）和 `reason`。AI 对自主开仓必须在提示中提交五项理由；任何缺项在记录和 UI 中都显示为“AI 未提供”，不会由后端补写主观理由。

### 3.2 平仓：`positions.exit_reasoning`

`positions` 增加可空 JSON 文本字段 `exit_reasoning`，只在仓位真正关闭后写入。内容包括版本、实际原因码、触发价格、记录者、来源和说明。

- AI 的组合风险复核平仓：保存其原始理由，标为 `system_operator`。
- 止损、止盈、最长持有期和市场规则退出：标为自动保护；说明会引用已经存储的保护价/时限，明确这不是新的 AI 判断。
- 人工、交易所确认及对账收敛：标明相应来源和已知证据；经济结果不明时继续显示未知，不推测价格或动机。

`close_position` 与经过路由的平仓仍按当前方式工作。说明仅在关闭事实已确认后保存；失败的交易所平仓绝不会留下“已平仓”的理由记录。

## 4. 页面呈现

在 Trades & Positions 的现有 Causal Chain 中新增两个只读节点：

1. **Entry reasoning**：紧随 Proposal，按五个要素展示最终数字、来源和理由，并列出名义价值、止损预计损失和保证金估算。
2. **Close reasoning**：紧随 Position。开仓中的仓位显示 `none`；旧的已平仓仓位显示 `not recorded`；有记录时显示实际平仓价、原因、执行者和原文/系统触发说明。

订单抽屉会从已有仓位列表按 `order_id` 找到对应仓位，因此已完成交易同样能展示平仓节点。该改动仅消除现有“订单找不到结果仓位”的显示缺口，不伪造成交或仓位。

## 5. 实施顺序

1. 在新 spec 中先声明“缺失”约束，写能证明现状不足的失败测试。
2. 扩展 AI 输出解析、提示词和提案理由元数据；最终数值全部在后端计算后才写入。
3. 增加仓位平仓说明字段及加法迁移；让普通、路由、自动和对账关闭各自写诚实来源。
4. 在因果侧栏解析并展示已保存记录；不解析失败的旧 JSON，不把缺失显示为正常。
5. 更新数据模型和交易执行说明，补齐 focused tests、spec、前端编译和流程验证。

## 6. 验收与验证

| 验收点 | 证明方式 |
|---|---|
| 五项开仓理由与最终数值一起保存 | 新增行为测试：市场价、默认止损/止盈、名义价值、实际数量和杠杆收紧均可从保存的 JSON 还原 |
| 理由受提案防篡改保护 | 现有 proposal hash 完整性测试与新增字段组合测试 |
| 所有关闭类型不伪装成 AI | 新增测试：自动止损、AI 组合复核、已验证成交和行政收敛分别保存正确 actor/source |
| 侧栏真实展示 | 前端源测试断言 Entry/Close 节点读取持久字段并保留缺失态；`npm run build` 通过类型检查 |
| 原有安全规则不变 | 聚焦 position-manager、proposal-rationale、decision-lifecycle、execution-chain specs；全量 specs、architecture fitness、doctor 与严格工作流检查 |

主工作树合并前，只在本隔离工作树运行代码与前端编译；不从空数据工作树重启 gateway。合并后才按项目 gateway 流程进行运行态验证。
